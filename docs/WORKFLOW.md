# Πώς δουλεύουμε (workflow)

Ισχύει για κάθε session με τον Claude σε αυτό το repo. Το αρχείο αλλάζει μόνο με PR· τα `/plan-week` και `/task`
(`.claude/skills/`) ακολουθούν ό,τι γράφει εδώ.

## 1. Μία λίστα

- Η λίστα εργασιών είναι η βάση **Tasks** στο Notion (Telematica → Tasks / Sprint board). Τη δομή της (views, πεδία,
  σελίδες) τη φτιάχνει και τη συντηρεί ο συνάδελφος· ο Claude δεν την αλλάζει.
- Κάθε GitHub issue που είναι δουλειά έχει κάρτα στο Notion (πεδίο `PR` = link στο issue ή στο PR). Το TEL-id της κάρτας
  μπαίνει στο branch και στον τίτλο του PR (`claude/TEL-<id>-<slug>`). Ποτέ TEL-id με το χέρι (#25).
- Ό,τι βρίσκουμε μέσα σε ένα session (bug, ιδέα, «αυτό θέλει αλλαγή») δεν διορθώνεται εκεί. Σημειώνεται (F1, F2…) και στο
  τέλος του session γίνεται issue + κάρτα (Not started, χωρίς sprint).

**Τι αλλάζει ο Claude στο Notion χωρίς να ρωτήσει** (μόνιμη άδεια του Kostas, 2026-10-17):
- νέες κάρτες στη βάση Tasks (Project = Telematica)·
- σε υπάρχουσες κάρτες: `Task status`, `Sprint` (μόνο μετά από απόφαση στο planning), `PR`, `Completed on`,
  `Who does this`, σύντομο κείμενο στο σώμα της κάρτας.

Όχι: views, πεδία ή σχήμα της βάσης, άλλες σελίδες, διαγραφή καρτών.

## 2. Τα δύο είδη session

### `/plan-week`: εβδομαδιαίο planning (χειροκίνητο)

Ξεκινά όταν το γράψει ο Kostas. Ορίζοντας: **μόνο η επόμενη εβδομάδα**. Τα sprints είναι δύο εβδομάδων, αλλά δεν
planάρουμε τόσο μπροστά. Σε αυτό το session δεν γράφεται κώδικας.

1. Ο Claude μαζεύει: κάρτες που δεν είναι Done, ανοιχτά GitHub issues και PRs.
2. Ελέγχει: issues χωρίς κάρτα, διπλά, κολλημένα (In progress / In review χωρίς κίνηση), PRs που περιμένουν merge,
   device tests που περιμένουν, αποφάσεις που εκκρεμούν.
3. Δείχνει μία σύντομη λίστα ανά ομάδα και πρόταση για **3–5 tasks** της εβδομάδας, με τον λόγο για το καθένα.
4. Κάνει όλες τις ερωτήσεις μαζί, αριθμημένες.
5. Ο Kostas αποφασίζει. Ο Claude ενημερώνει τις κάρτες (Sprint, Who does this) και φτιάχνει όσες έλειπαν.
6. Τέλος: η λίστα της εβδομάδας με σειρά, και ποιο είναι το πρώτο `/task`.

### `/task TEL-<id>`: ένα task ανά session

1. **Κατανόηση.** Ο Claude διαβάζει κάρτα, issue και σχετικό κώδικα και γράφει σε 3 γραμμές: στόχος, «τελειώνει όταν»,
   τι δεν περιλαμβάνει. Ό,τι είναι ασαφές το ρωτά, όλα μαζί.
2. **Σχέδιο.** Σε απλά λόγια: τι αλλάζει, ποια αρχεία, πώς θα ελεγχθεί. Περιμένει έγκριση.
3. **Υλοποίηση.** Κάρτα → In progress, branch, αλλαγές, `npm test` + `npm run check:i18n`, `npm run shots` για ό,τι
   φαίνεται στην οθόνη. Draft PR με το template και τις 3 γραμμές explain-back. Κάρτα → In review, `PR` = link.
4. **Έλεγχος από τον Kostas.** Βήμα-βήμα (ενότητα 3), μόνο για ό,τι δεν δείχνει το `shots` (κανόνας 9 στο CLAUDE.md).
5. **Merge.** Μόνο ο Kostas. Ο Claude λέει πότε το CI είναι πράσινο και δίνει το link.
6. **Κλείσιμο.** Κάρτα → Done + `Completed on`, findings → issues + κάρτες, σύνοψη: τι έγινε, τι μένει, πρόταση για το
   επόμενο task.

Ένα task = ένα branch = ένα PR. Αν το task βγαίνει μεγάλο (> ~3 αρχεία ή δύο θέματα), ο Claude προτείνει να σπάσει πριν
ξεκινήσει.

## 3. Κανόνας βημάτων

Κάθε βήμα που κάνει ο Kostas γράφεται έτσι:

> **Βήμα N. Κάνε μόνο αυτό και απάντησε.**
> - Τι κάνεις: η εντολή, το κλικ ή το URL, ακριβώς.
> - Τι κάνει, σε μία πρόταση.
> - Τι περιμένουμε να δεις.
> - Τι μου απαντάς (π.χ. «done» + τις τελευταίες 2–3 γραμμές, ή απαντήσεις a/b/c).

- Ένα βήμα τη φορά. Το επόμενο βήμα δεν δίνεται πριν την επιβεβαίωση.
- Αν το αποτέλεσμα διαφέρει από το αναμενόμενο, σταματάμε: ο Claude εξηγεί τι σημαίνει και δίνει διορθωτικό βήμα.
- Παρατηρήσεις πάνω σε ένα βήμα γίνονται findings, δεν αλλάζουν το τρέχον task.

**Η δουλειά του Claude:**
- Χωρίς ερώτηση (αναφέρει το αποτέλεσμα): διάβασμα κώδικα και docs, τεστ, `npm run shots`, commits και push στο δικό
  του branch, draft PR, διορθώσεις CI στο δικό του PR, κάρτες Notion όπως στην ενότητα 1.
- Πάντα με έγκριση: το σχέδιο πριν τον κώδικα, κλείσιμο ή αλλαγή issues, αλλαγές εκτός του task.
- Ποτέ: merge, push στο `main`, deploy του worker (μόνο ο Kostas), secrets σε αρχεία.
